# 플랫폼 알림 서비스(doro-notify) 설계

> 상태: **D1~D3 승인됨(2026-10-20, 권고안 그대로).** 이 문서는 설계만 다룬다. 구현·배포·운영 설정 변경은 별도 지시 뒤에 하고, 파티 이관은 파티 푸시 안정화(1~2주) 뒤에 한다.
> 작성 기준일: 2026-10-20. 근거는 코드로 확인한 현황(2장)이고, 확인하지 못한 것은 "미검증"으로 표시했다.

## 1. 목적과 범위

알림 기능이 서비스마다 흩어져 있다. 파티는 웹 푸시와 설정을 갖고, 블로그는 앱 안 알림함만 있고, 게임·메뉴·허브는 알림이 없다. 새 서비스가 알림을 쓰려면 푸시 암호화·VAPID·구독 관리를 다시 만들어야 하고, 사용자는 알림 설정을 앱마다 따로 찾아야 한다.

**목표**: 기기 등록·알림 설정·발송을 한 서비스로 모으고, 허브 "내 계정"에서 앱별·종류별 설정과 내 기기 목록을 보여 준다.

**이번 범위(권고)**: 웹 푸시의 기기 등록, 설정, 발송. 첫 소비자는 파티, 두 번째는 블로그.

**범위 밖**: 통합 알림함(블로그 알림함 이관), 방해금지 시간, 이메일·문자 채널, 별도 메시지 브로커. 이유는 14장.

## 2. 현황 (코드로 확인)

| 서비스 | 알림 | 비고 |
| --- | --- | --- |
| 파티 | 웹 푸시(운영 중, 2026-10-19~) | RFC 8291·8292를 JDK 암호 API로 구현. 구독·설정 테이블 `push_subscriptions`, `push_preferences`(V13). 알림 4종(새 댓글·답글, 친구 요청·수락, 지도 공유). 보낼 때 Guard로 수신자 권한 재확인 |
| 블로그 | 앱 안 알림함 | `notifications` 테이블(V4), 종류 COMMENT/REPLY/LIKE/FOLLOW. 푸시·설정 없음 |
| 게임·메뉴·허브 | 없음 | |

공통 구조는 이렇다.

- 앱마다 별도 PWA와 서비스 워커(SW)가 있다. 허브 `/`, 블로그 `VITE_BASE_PATH`, 게임 `/games/`, 파티 `/party/`, 메뉴 `./`.
- 서비스 간 내부 호출은 `X-Doro-Service-Token` 헤더(이름:토큰 목록)로 인증한다(IAM `InternalApiAuthFilter`). 게이트웨이를 거친 요청(`X-Forwarded-For`/`X-Real-IP`)은 404로 막는다.
- 탈퇴 사용자 동기화는 SDK `DeletedUsersSync` + `DeletedUserHandler`로 한다.
- 파티는 이미 아웃박스 패턴을 쓴다(`GuardTupleDeleteOutbox` + 재시도기).

## 3. 핵심 기술 제약과 그 결과

1. **푸시 구독은 서비스 워커 등록(범위)에 묶인다.** 구독을 만든 SW로만 전달된다. "구독 하나로 전 앱"은 불가능하다. 한 기기에는 앱 수만큼 구독이 생긴다.
2. **알림 권한(`Notification.permission`)은 출처 단위**다. 한 번 허용하면 모든 앱에 적용된다.
3. 따라서 **구독 생성과 클릭 처리는 앱별 SW에 남기고, 기기 등록·설정·발송은 중앙화**한다.
4. 같은 출처에 있으니 `localStorage`도 앱 사이에 공유된다. 이 점을 "같은 기기" 식별에 쓴다(8장).

## 4. 결정 사항과 권고

| # | 질문 | 권고 | 대안과 이유 |
| --- | --- | --- | --- |
| D1 | 범위 | **푸시 설정·기기 관리까지** | 통합 알림함까지 가면 블로그 `notifications` 이관이 필요하다. 위험·비용이 크고, 푸시를 중앙화하는 가치와는 별개다. 알림함은 푸시가 안정된 뒤 따로 판단한다 |
| D2 | 형태 | **독립 서비스** | 공통 라이브러리는 코드 중복만 줄이고, 설정·기기 데이터가 서비스마다 남아 허브에서 한 화면으로 못 보여 준다. 그래서 "한 곳에서 관리"라는 목적을 못 이룬다 |
| D3 | 허브 위치 | **"내 계정" 안에 "알림" 섹션 신설**(기기 관리 섹션 가까이) | 별도 페이지는 진입점이 늘어난다. 앱별 켜기·끄기는 8장의 제약 때문에 앱 화면으로 넘기는 보조 경로를 둔다 |

## 5. 서비스 경계와 소유 데이터

MSA 매뉴얼 1장 기준(불변식이 함께 필요한가)으로 나눈다.

**알림 서비스가 소유**: 기기·구독, 알림 설정(앱별·종류별), 알림 종류 등록부, 발송 큐와 결과, 멱등 키.
**각 서비스가 소유**: 수신자 계산, 수신자 권한 확인(Guard), 문구, 눌렀을 때 주소, 알림을 보낼지의 업무 규칙. 알림 서비스는 이것들을 모른다.

경계 점검:
- 구독 등록과 설정 변경은 알림 서비스 안의 로컬 트랜잭션 하나로 끝난다.
- 댓글 저장과 알림 요청은 서비스 둘에 걸친 쓰기지만, 알림은 부가 기능이고 어긋나도 안전하다(알림이 안 갈 뿐). 그래서 Saga가 아니라 4.6의 가벼운 방법(아웃박스 + 재시도 + 점검)을 쓴다.
- 서비스 사이는 `userId`로만 참조한다.

**알림 서비스에 업무 규칙을 두지 않는다.** "내가 쓴 댓글은 나에게 알리지 않는다" 같은 규칙은 요청을 보내는 서비스에 남긴다. 알림 서비스가 하는 판단은 (a) 사용자가 이 종류를 껐는가, (b) 같은 요청이 이미 왔는가, (c) 보낼 기기가 있는가 세 가지뿐이다.

## 6. 데이터 모델

DB는 `service_notify`, Flyway 이력은 `notify_schema_history`, `ddl-auto: validate`. (신규 서비스 표준 절차 1단계)

```
notify_apps            -- 앱 등록부(생산자 서비스)
  app_id        text PK            -- 'party','blog','games','menu','hub'
  scope_path    text               -- 클릭 주소 허용 범위. 예 '/party/'
  display_name  text

notify_types           -- 알림 종류 등록부
  app_id, type_id   PK
  label         text               -- 허브 화면 표시명
  default_on    boolean
  description   text

push_subscriptions
  id            uuid PK
  user_id       uuid               -- IAM 사용자 ID
  app_id        text               -- 이 구독을 만든 SW 의 앱
  device_id     text               -- 클라이언트가 만든 기기 표식(그룹핑용, 8장)
  endpoint      text   UNIQUE      -- 로그·응답에 남기지 않는다
  p256dh, auth  text               -- 로그·응답에 남기지 않는다
  user_agent    text
  fail_count    int
  created_at, last_success_at, last_seen_at

notify_preferences
  user_id, app_id, type_id  PK
  enabled       boolean            -- 행이 없으면 default_on

delivery_jobs          -- 구독 단위 발송 큐(재시도용)
  id, request_id, subscription_id
  payload       bytea/json         -- 암호화 전 페이로드, 발송 끝나면 비운다
  status        PENDING|SENT|FAILED|DROPPED
  attempts, next_attempt_at, expires_at, last_status

notify_requests        -- 요청 단위 기록 + 멱등 키
  id, caller, idempotency_key  UNIQUE(caller, idempotency_key)
  app_id, type_id, recipient_user_id
  outcome       ACCEPTED|SUPPRESSED_PREF|NO_SUBSCRIPTION|DUPLICATE
  created_at                       -- 보관 14일, 이후 삭제
```

- 알림 **내용(제목·본문)은 요청 기록에 영구 저장하지 않는다.** 큐에 있는 동안만 두고 발송 후 비운다. 로그에도 남기지 않는다.
- 사용자당 구독 상한을 둔다(파티는 기기 10대). 앱이 여러 개이므로 상한은 **(사용자, 앱)당 10개**로 시작한다.

## 7. API

### 7.1 클라이언트용 (로그인 사용자, 게이트웨이 경유)

**인증 경로 (게이트웨이·BFF 설정을 읽고 확인한 결과)**: 앱마다 인증 방식이 달라 한 경로로 통일할 수 없다.

- 파티·게임의 BFF 세션 쿠키는 경로가 `/party`, `/games`로 제한된다(`cookie-path`). `/notify/...` 요청에는 이 쿠키가 실리지 않는다. 블로그 쿠키만 경로가 `/`다. 허브는 쿠키가 아니라 IAM 액세스 토큰(Bearer)으로 호출한다.
- 그래서 **앱 화면은 자기 접두사 아래로 호출**한다: 게이트웨이에 `/party/api/v1/notify/`, `/blog/api/v1/notify/`, `/games/api/v1/notify/` location을 추가해 알림 서비스로 프록시하고, 기존 `auth_request /_bff_auth_<app>`과 `Authorization $bff_authorization`을 그대로 쓴다. 호출한 앱 식별(`app`)은 **본문이 아니라 이 location이 정해 헤더로 붙인다**(클라이언트가 다른 앱 행세를 못 하게).
- **허브는 `/notify/api/v1/`로 Bearer 토큰** 호출한다. 알림 서비스는 두 경우 모두 SDK로 JWT를 검증한다. 허브 경로는 `app`을 지정하지 않고 설정 조회·변경과 기기 해제만 허용한다(구독 등록은 앱 경로에서만).
- 쿠키로 상태를 바꾸는 요청의 CSRF 증명은 기존 앱 API와 같은 규칙을 따른다(게이트웨이 `@bff_forbidden`).

아래 표의 경로는 모두 위 두 접두사 아래의 같은 하위 경로다.

| 메서드 | 경로 | 설명 |
| --- | --- | --- |
| GET | `/config` | VAPID 공개 키, 서버 사용 가능 여부 |
| PUT | `/subscriptions` | 구독 등록(upsert). 본문: `app`, `deviceId`, `endpoint`, `keys`. 허용 목록·곡선 검증 통과해야 받는다 |
| DELETE | `/subscriptions` | 구독 하나 해제(본문 endpoint). 내 것만, 없어도 성공 |
| DELETE | `/devices/{deviceId}` | 이 기기의 모든 앱 구독 해제(로그아웃 때 사용) |
| GET | `/devices` | 내 기기 목록(기기별로 묶고 앱별 켜짐 상태, 마지막 성공 시각, 브라우저 종류). endpoint·키는 안 준다 |
| GET | `/preferences` | 앱·종류별 설정(종류 등록부와 합쳐 라벨 포함) |
| PUT | `/preferences` | 설정 변경 |
| POST | `/test` | 내 기기로 시험 알림 |

### 7.2 서비스 간 내부 API

경로 `/internal/v1`. 게이트웨이가 라우팅하지 않는다. 호출자 서비스 토큰(`X-Doro-Service-Token`)으로 호출자를 식별하고, 도입 시 OFF/WARN/ENFORCE 단계를 따른다(IAM과 동일). 호출자는 **자기 `app_id`로만** 요청할 수 있다(토큰 이름과 `app` 일치 검사).

**알림 요청** `POST /internal/v1/notifications`

```json
{
  "idempotencyKey": "comment:6f1c…",
  "app": "party",
  "type": "comment",
  "recipients": ["<userId>", "…"],
  "title": "핀 이름",
  "body": "작성자: 댓글(140자 이내)",
  "tag": "pin:<pinId>",
  "url": "/party/?map=…&pin=…",
  "ttlSeconds": 86400,
  "urgency": "normal",
  "expiresAt": "2026-10-20T12:00:00Z",
  "dryRun": false
}
```

- `recipients`는 **서비스가 이미 계산하고 권한까지 확인한 목록**이다. 알림 서비스는 다시 판단하지 않는다.
- `idempotencyKey`는 호출자 안에서 유일해야 한다. 같은 키 재요청은 오류 없이 200으로 `DUPLICATE`를 돌려준다(수신자별로 키를 나누지 않고 요청 단위, 수신자별 중복은 `(요청, 수신자)`로 막는다).
- `url`은 등록된 `scope_path` 안의 상대 경로여야 한다. 밖이면 400.
- `tag`는 같은 알림을 합칠 때 쓴다(푸시의 `tag`/`Topic`). 기기가 꺼져 있는 동안 쌓이지 않는다.
- `expiresAt`이 지나면 재시도하지 않고 버린다(낡은 알림이 늦게 오지 않게).
- `dryRun`은 이관 검증용(12장): 설정·구독 판정은 하고 실제 전송만 안 한다.
- 응답은 즉시 반환(큐 적재 기준)이다: `{accepted, suppressed, noSubscription}` 수신자 수. 실제 전송은 비동기.
- 동기 호출이므로 호출자는 **타임아웃(연결 2초·읽기 3초)** 을 두고, 호출은 커밋 후에만 한다.

**종류 등록** `PUT /internal/v1/apps/{app}/types` — 서비스가 기동할 때 자기 알림 종류(`typeId`, 라벨, 기본값)를 등록한다(upsert, 멱등). 허브 화면의 문구 출처이다. 종류를 지우지는 않고 `deprecated`로 표시한다.

**탈퇴** 별도 API 없이 SDK `DeletedUserHandler`로 사용자의 구독·설정을 지운다(SDK 동기화 설정은 `enable-deleted-sync.sh` 절차 참고).

### 7.3 페이로드 계약 (푸시 메시지, 버전 1)

기기로 가는 JSON. 앱별 SW가 이 모양만 알면 된다.

```json
{ "v": 1, "app": "party", "type": "comment", "title": "…", "body": "…", "tag": "…", "url": "/party/?…", "icon": "…" }
```

알 수 없는 `v`는 SW가 무시하지 않고 `title`/`body`만으로 표시한다(앞·뒤 호환).

## 8. 클라이언트: 앱별 서비스 워커와 구독

구독 생성과 클릭 처리는 앱 SW에 남긴다.

- **푸시 수신**: 앱별 `push-sw.js`는 7.3 계약대로 `showNotification`만 한다. 파티의 `push-sw.js`를 기반으로 공통 부분(수신, 계약 파싱)과 앱별 부분(클릭 처리)을 나눈다.
- **클릭 처리는 앱 소유**: 파티의 단계적 딥링크 처리(창 앞으로 → 앱 안 이동 → 직접 이동 → 새 창, 앱 범위 밖 주소 거부)는 그대로 파티에 둔다. 블로그는 블로그 방식으로 쓴다. 알림 서비스는 `url`만 준다.
- **구독**: 앱 코드가 `pushManager.subscribe`(알림 서비스의 VAPID 공개 키)를 하고 `PUT /subscriptions`로 등록한다. 파티의 `web/src/push/`, `pushStore`를 알림 서비스 API를 쓰도록 바꾼다.
- **기기 표식(`deviceId`)**: 같은 출처의 `localStorage`에 UUID를 저장해 앱 사이에 공유한다. 허브가 앱별 구독을 한 기기로 묶는 데 쓴다. 저장소가 비면(브라우저 데이터 삭제) 새 기기로 보이고, 옛 구독은 만료 정리(404/410)로 사라진다. 완벽한 식별이 아니라 **표시용 그룹핑**이다.
- **공통 코드 배포**: 앱이 별도 저장소라서 공통 클라이언트 코드(구독·등록·계약 파싱)는 복사 또는 작은 패키지로 나눈다. 방식은 열린 질문(15장).
- **허브에서 다른 앱 구독 켜기(부분 검증)**: 헤드리스 Chromium에서 같은 출처의 허브 페이지(`/`)가 `navigator.serviceWorker.getRegistration('/party/')`로 파티 SW 등록을 얻고, 활성 상태와 `pushManager`에 접근하며, `subscribe`가 파티 화면 안에서 호출했을 때와 **똑같이 동작**함을 확인했다(스크래치 테스트, 저장소에 넣지 않음). 다만 헤드리스에는 푸시 서비스가 없어 실제 구독 생성은 두 경우 모두 같은 오류로 끝났다. **실제 FCM 구독, 파티가 아닌 다른 앱, iOS 홈 화면 앱은 확인하지 못했다.** 앱 SW가 한 번도 설치되지 않았으면 등록 자체가 없으므로 허브는 켜기를 못 한다. 그래서 허브는 **끄기·설정을 직접 하고, 켜기는 앱 화면 링크를 기본**으로 하고 허브 직접 켜기는 실기기 확인 뒤의 부가 경로로 둔다.
- **로그아웃**: 앱은 로그아웃 전에 `DELETE /devices/{deviceId}`로 이 기기를 먼저 뗀다(파티가 지금 하는 것과 같은 의도: 이전 계정 알림이 이 기기로 오지 않게). 실패해도 로그아웃은 막지 않는다.
- **VAPID 키**: 파티가 쓰는 키를 그대로 알림 서비스가 쓴다. 이미 등록된 기기가 재구독 없이 이어진다. 키를 바꾸면 모든 구독이 무효다.

## 9. 허브 "내 계정" 알림 섹션

`MyAccountPage`의 "내 로그인 기기 관리" 부근에 "알림" 섹션을 넣는다.

1. **상단 상태**: 이 브라우저의 알림 권한(허용/차단/미요청)과 서버 사용 가능 여부. 차단이면 브라우저 설정 안내.
2. **앱별 카드**: 앱 이름 아래 종류별 토글(라벨은 종류 등록부에서). 이 기기에서 해당 앱 알림이 켜져 있는지 표시, 꺼져 있으면 "앱에서 켜기" 링크.
3. **내 기기 목록**: 기기별(브라우저·마지막 성공 시각·켜진 앱 목록), 기기별 "이 기기 해제".
4. **시험 알림** 버튼.

앱 안(파티의 헤더 종 아이콘 설정 시트)은 그대로 남기고, 같은 서버 설정을 읽고 쓴다. 허브와 앱 중 어디서 바꿔도 같은 값이다.

## 10. 보안

- **구독 주소 허용 목록(SSRF)**: 알려진 푸시 서비스 도메인의 https·기본 포트만 받는다. IP, 계정 정보 포함 주소, 허용 밖 도메인은 거절. **저장된 주소를 보낼 때 다시 검증**하고 리디렉션은 따르지 않는다. 파티 `PushEndpointPolicy`를 이관한다.
- **p256dh 곡선 검증**: 곡선 위의 점인지 확인(잘못된 곡선 공격 방지).
- **내 것만**: 구독 해제·설정은 인증된 `userId` 소유 행에만 적용한다. 다른 사용자의 endpoint를 알아도 지울 수 없다. 같은 endpoint가 다른 계정으로 오면 소유가 옮겨진다(같은 기기 계정 전환).
- **수신자별 권한은 요청하는 서비스의 책임(fail-closed)**: 파티가 지금 보낼 때 Guard로 받는 사람의 권한을 다시 확인한다. 이 규칙은 **요청을 보내기 직전, 파티 쪽에서** 한다. Guard가 응답하지 않으면 요청하지 않는다. 알림 서비스는 Guard를 호출하지 않는다.
  - 트레이드오프: 확인 시점이 "발송 직전"에서 "요청 직전"으로 앞당겨진다. 사이의 시간은 큐 지연뿐이라 짧고, `expiresAt`으로 오래된 재시도를 버려 창을 줄인다.
- **호출자 인증**: 내부 API는 서비스 토큰 + 게이트웨이 미경유 요건. 호출자는 자기 `app`만 쓸 수 있다. 토큰은 환경 변수로만 주고 로그에 남기지 않는다.
- **로그에 비밀 금지**: endpoint·p256dh·auth·VAPID 개인 키·알림 본문을 로그·응답·오류 메시지에 남기지 않는다(호스트와 상태 코드만).
- **VAPID 개인 키**는 알림 서비스만 가진다. 파티 이관 뒤 파티 환경에서 제거한다(12장).
- **페이로드 크기·수신자 수 상한**을 둔다(요청 하나당 수신자 N명 이내). 상한을 넘으면 400.
- **개인정보 최소화**: 알림 본문은 발송 후 저장하지 않는다. 푸시 서비스는 내용을 볼 수 없다(암호화).
- **탈퇴**: 사용자 동기화로 구독·설정을 삭제한다(파티가 지금 익명화 때 삭제하는 것과 같은 정책).

## 11. 신뢰성과 정합성

- **요청 측(각 서비스)**: 커밋 후에 보낸다. 서비스가 `notify_outbox` 테이블에 요청을 **같은 트랜잭션에서** 저장하고 재시도기가 호출한다(파티 `GuardTupleDeleteOutbox` 패턴 재사용). 알림 서비스가 죽어 있어도 댓글 저장은 영향이 없고, 복구되면 보낸다. 재시도는 멱등 키가 있으니 안전하다. 재시도는 지수 백오프·횟수 상한, `expiresAt`이 지나면 포기한다.
  - 대안: 파티가 지금 쓰는 "커밋 후 메모리 이벤트 + 대기열이 가득 차면 버림" 방식을 유지하면 구현이 단순하지만, 프로세스 재시작 때 알림이 사라진다. 알림이 부가 기능이라는 점에서 허용 가능하나, 서비스 간 호출이 하나 끼므로 **아웃박스를 권고**한다. (15장에서 확인)
- **알림 서비스 측**: 요청을 받으면 `notify_requests`(멱등 키)와 `delivery_jobs`를 **한 트랜잭션**으로 저장하고 응답한다. 워커가 큐를 `FOR UPDATE SKIP LOCKED`로 가져와 보낸다. 일시 오류(시간 초과·429·5xx)는 백오프 재시도(파티는 현재 재시도가 없다: 개선점)하되 TTL·`expiresAt` 안에서만. 404/410은 구독 삭제, 거절(키 불일치 등)이 5번 연속이면 삭제. 일시 오류로는 지우지 않는다.
- **합치기·중복 방지**: 같은 요청 키는 한 번만 처리. 같은 `tag`는 푸시 서비스가 한 알림으로 합친다.
- **알림 서비스 장애 시 영향**: 푸시만 멈춘다. 설정 화면은 오류를 보여 주되 앱 본 기능은 막지 않는다. VAPID 키가 없으면 푸시만 꺼진다(지금과 동일).
- **정합성 점검(주기 작업)**:
  - 탈퇴한 사용자의 구독·설정이 남았는지 정리(동기화 누락 보강).
  - 오래 성공이 없는 구독 정리, 오래된 `delivery_jobs`·`notify_requests` 삭제.
  - 요청 서비스의 `notify_outbox`에 오래 남은 건이 있는지 감시.
- **타임아웃**: 서비스→알림 서비스 호출은 연결 2초·읽기 3초. 알림 서비스→푸시 서비스는 짧은 타임아웃과 전용 스레드 풀(벌크헤드).

## 12. 파티 이관 계획

**시점**: 파티 푸시는 운영 시작 직후이고 실사용 버그가 나오는 중이다. **1~2주 안정화 뒤에 시작**한다. 그 전에는 이 문서만 둔다.

모드 스위치 `party.push.mode`: `LEGACY` → `SHADOW` → `CENTRAL`.

| 단계 | 내용 | 확인 |
| --- | --- | --- |
| P0 | 알림 서비스 구현·배포(소비자 없음). 파티 구독 데이터를 알림 서비스로 **가져오기**(같은 VAPID 키라 재등록 불필요, 일회성 스크립트, 멱등) | 가져온 행 수 = 파티의 행 수, 허용 목록 검증 통과 |
| P1 `SHADOW` | 파티는 **지금처럼 직접 발송**하면서 같은 알림을 알림 서비스에 `dryRun:true`로도 요청. 알림 서비스는 판정만 하고 전송하지 않음 | 파티가 보낸 수신 기기 수와 알림 서비스가 "보냈을" 기기 수를 비교(불일치 0). 설정 차이, 구독 누락이 여기서 드러남 |
| P2 `CENTRAL` | 파티는 요청만 하고 직접 발송 중단. 클라이언트도 알림 서비스 API로 구독·설정 | 실제 폰에서 4종 알림 수신, 로그아웃 분리, 탈퇴 정리 확인 |
| P3 | 2주 안정화 뒤 파티의 옛 코드·테이블·VAPID 키 제거 | |

**롤백**: P2에서도 파티의 옛 발송 코드와 `push_subscriptions`·`push_preferences`는 **지우지 않는다**. `party.push.mode`를 `LEGACY`로 돌리면 파티가 다시 직접 발송한다. 단 P2 중 새로 등록·해제·설정 변경된 값은 파티 쪽에 없다. 롤백 시 알림 서비스 → 파티로 **역가져오기**(P0 스크립트의 반대) 한 번을 실행한다. 이 스크립트를 P2 시작 전에 준비하고 한 번은 시험한다. P3 전까지만 롤백이 쉽다.

**클라이언트 전환**: 파티 프런트가 새 API로 바뀌면, 이미 열려 있는 옛 화면(PWA는 며칠씩 다시 로드되지 않는다)이 옛 파티 API를 부를 수 있다. 파티의 옛 `/api/v1/push/*`는 P3까지 유지하고, P2 중 옛 API로 온 변경은 알림 서비스로 전달하거나(모드가 `CENTRAL`이면 파티가 새 서비스에 위임) 최소한 오류가 안 나게 한다. 선택은 15장.

**검증**: 파티에 있는 RFC 8291 테스트 벡터(바이트 단위 일치)·받는 쪽 복호화·실제 FCM 연동 확인(`PushLiveInteropTest`) 테스트를 **코드와 함께 이관**한다. 이관 뒤에도 같은 테스트가 통과해야 한다. 알림 4종은 실제 폰으로 확인한다.

## 13. 블로그 연동 (두 번째 소비자)

블로그 `notifications` 테이블과 알림함은 **그대로 둔다**. 블로그가 알림을 DB에 저장하는 같은 지점에서, 커밋 후 알림 서비스에 요청을 추가한다(COMMENT/REPLY/LIKE/FOLLOW 4종). 종류는 `PUT /internal/v1/apps/blog/types`로 등록한다. 수신자 계산은 이미 블로그가 하고 있다. 새 서비스 워커 푸시 처리와 구독 UI(블로그 `VITE_BASE_PATH` 범위)를 추가한다. 좋아요는 양이 많아질 수 있으니 `tag`로 합치는 정책을 정한다(블로그가 결정). 파티 이후 다중 서비스 검증이 된다.

## 14. 하지 않는 것과 이유

- **통합 알림함**: 블로그 알림함 이관은 위험·비용이 크고 가치가 낮다. 푸시 중앙화와 독립적이다.
- **방해금지 시간**: 사용자 요구가 확인되지 않았다. 설정 모델에 추가하기 쉬운 구조(앱·종류 키)라서 나중에 붙일 수 있다.
- **이메일·문자**: 채널 추상화를 지금 만들지 않는다. `delivery_jobs`에 `channel` 열을 두지 않고, 필요할 때 추가한다.
- **별도 메시지 브로커**: 서비스 DB의 아웃박스 + 큐 테이블로 충분하다(트래픽이 작고 팀이 하나).

분리의 정당성(매뉴얼 0장): 이 서비스는 팀 분리 때문이 아니라 **다섯 소비자가 같은 기능을 공유**하고 **사용자 데이터(기기·설정)가 한 곳에 있어야 허브가 보여 줄 수 있다**는 이유다. 규모가 작아 서비스 하나가 더 늘어나는 운영 비용(컨테이너·DB·CI·토큰 관리)은 감수한다. 이 비용이 크다고 판단되면 대안은 "IAM 안의 모듈"이지만 IAM 책임이 흐려지므로 권고하지 않는다.

## 15. 열린 질문

1. **D1·D2·D3 확인** (4장).
2. ~~클라이언트 API 인증 경로~~ **해소**: 앱 접두사 아래 프록시 + 허브는 Bearer(7.1). 메뉴는 현재 로그인이 없어 대상이 아니고, 메뉴가 로그인·알림을 도입하는 업데이트 때 소비자로 추가한다(`/menu/api/v1/notify/` 접두사와 `notify_apps` 등록만 늘어나며 설계 변경은 없다). 허브 자체의 푸시는 이번 범위 밖.
3. **허브에서 다른 앱 구독 켜기**(8장): 크로미엄에서 등록 접근은 확인, 실제 구독·iOS는 실기기 확인 필요(구현 중 파티로 시험).
4. **공통 클라이언트 코드 배포 방식**: 확인 결과 앱 저장소 사이에 공유 프런트 코드의 선례가 없다(PWA 코드는 파티에만 있고, 공유 npm 패키지·레지스트리 설정도 없다). **권고는 복사**: 구독·등록·계약 파싱은 작은 모듈이라 파일 하나를 각 앱에 두고, 파일 머리에 계약 버전(`v1`)을 적고, 알림 서비스 쪽에 계약 테스트를 둬서 어긋남을 잡는다. 패키지화는 앱이 4개를 넘으면 다시 본다.
5. **내부 인증 필터를 SDK로 올릴지**: 확인 결과 `InternalApiAuthFilter`는 IAM(`auth` 모듈)에만 있고 SDK에는 호출 쪽(`ServiceTokenClientInterceptor`)만 있다. 권고는 알림 서비스에 같은 방식의 필터를 두는 것(작은 코드). SDK로 올리는 것은 두 번째 수신 서비스가 생길 때 한다. 알림 서비스가 같은 필터가 필요하다.
6. **아웃박스 vs 메모리 이벤트**(11장): 부가 기능이라는 점과 구현 비용 사이의 선택. 권고는 아웃박스.
7. **파티 이관 중 옛 화면의 옛 API 처리**(12장).
8. **Guard 스키마**: 알림 서비스 컨트롤러는 사용자 본인 데이터만 다뤄서 Zanzibar 타입이 필요 없다고 보지만, `@DoroGuard` 적용 여부(표준 절차 2~3단계)를 확인해야 한다. 스키마 등록은 병합 절차 필수.
9. **인프라 변경은 승인 뒤**: 게이트웨이 location(`nginx.conf`는 compose 밖에서 손으로 반영)과 `scripts/gateway-routing/expect-current.txt`, compose, CI, 서비스 토큰 발급은 구현 승인 뒤에 한다.

## 16. 관측성과 운영

- **traceId**: 요청 서비스가 `X-Trace-Id`를 알림 요청에 실어 보내고, 알림 서비스는 MDC에 바인딩해 큐 작업·푸시 호출 로그까지 같은 ID로 남긴다. 로그는 stdout, 수집기가 가져간다.
- **상태 조회**: 관리자용 내부 조회로 `delivery_jobs`의 상태별 건수, 가장 오래된 PENDING 나이, 앱별 최근 24시간 accepted/sent/dropped/failed, 푸시 서비스 응답 코드 분포를 본다.
- **알림(운영 경고)**: 큐에 오래 머문 건, 연속 실패 급증(404/410 급증은 키 변경·SW 문제 신호), 요청 서비스 아웃박스 적체, 재시도 소진 건.
- **재시도 소진 건**: 알림은 부가 기능이라 소진된 건은 `FAILED`로 남기고 사람이 개입하지 않는다. 원인(키·허용 목록·푸시 서비스 장애)만 조사한다. 절차는 구현 때 운영 문서에 추가한다.

## 19. 구현 현황 (Doro 저장소 쪽)

18장의 3단계(허브 알림 섹션)와 게이트웨이 연결 지점까지 Doro 저장소에 넣었다. 알림 서비스 본체(`doro-notify`)는 별도 저장소다. 서버 반영과 17장의 나머지 항목은 배포 단계에서 한다.

**들어간 것**
- 허브 알림 섹션: `web/src/components/notifications/NotificationSettingsSection.tsx`, API 클라이언트 `web/src/api/notifyApi.ts`, 순수 로직 `web/src/utils/notifySettings.ts`. "내 계정 > 기기 및 세션" 탭 아래에 붙는다. 허브에서 다른 앱의 구독을 직접 만드는 기능은 넣지 않았다(8장). 서버가 없거나 내려가 있으면(404·502·503·504) 이 섹션만 "사용할 수 없음"으로 보인다.
- 게이트웨이(`gateway/nginx.conf` 참고 사본): upstream `notify_api_upstream`(api 포트 8089)과 location 4개. 허브용 `/notify/api/v1/`은 Bearer를 그대로 넘기고 클라이언트의 `X-Doro-Notify-App`을 지운다. 앱용 `/party|blog|games/api/v1/notify/`는 각 앱의 `auth_request`를 쓰고 `X-Doro-Notify-App`을 location이 고정한다. `/internal/v1/**`은 라우팅하지 않는다. 라우팅 시험(`scripts/test-gateway-routing.sh`)은 위조 헤더가 덮어써지는지도 확인한다.
- 개발 서버 프록시: `/notify/api/v1`을 알림 서비스의 `/api/v1/notify`로 넘긴다(`VITE_DEV_NOTIFY_TARGET`).

**허브 쪽 가정(백엔드 확정 시 `notifyApi.ts` 타입만 맞춘다)**
- 응답은 플랫폼 공통 봉투 `{ success, data }`다.
- `GET /config` → `{ available }`, `GET /preferences` → 앱 배열(`app`, `displayName`, `types[]`: `type`, `label`, `description`, `enabled`, `deprecated`), `GET /devices` → `{ deviceId, browser, lastSuccessAt, apps[] }` 배열, `PUT /preferences` 본문 `{ app, type, enabled }`, `POST /test` → `{ sent }`.
- 기기 표식(`deviceId`)은 같은 출처의 `localStorage` 키 `doro.notify.deviceId`에서 읽는다. 허브는 읽기만 하므로 앱의 구독 코드가 같은 키로 쓰기로 정해야 한다.

**내부 토큰 호출자 이름 규칙**: 서비스 토큰(`X-Doro-Service-Token`)의 `이름`은 요청 본문 `app`과 같은 `app_id`(`party`, `blog` ...)로 한다. 알림 서비스가 "토큰 이름과 `app` 일치"를 검사하므로(7.2) 호출자마다 자기 `app_id` 이름으로 토큰을 한 개씩 발급한다. 값은 문서·로그에 쓰지 않는다.

**배포 단계에서 할 것(이 변경에 포함하지 않음)**
- 서버 게이트웨이 설정에 위 location 반영(참고 사본과 같은 내용을 서버에서 손으로 적용하고 `nginx -t` 후 reload). 앞의 기존 앱 location(`/party/api/` 등)은 건드리지 않으며, 더 긴 접두사라 순서와 무관하게 먼저 맞는다.
- `docker-compose.yml`에는 notify를 넣지 않는다(서비스 저장소의 compose로 따로 운영). DB `service_notify`와 계정 `notify_app` 생성은 `scripts/split-db-accounts.sh`, 스모크 항목은 `scripts/post-deploy-smoke.sh`에 서비스가 서버에 뜬 뒤 별도 PR로 추가한다(먼저 넣으면 스모크가 실패한다).
